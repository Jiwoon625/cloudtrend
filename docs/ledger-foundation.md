# Unified journal foundation, tranche 1

Status: implementation and SQL **review draft**, not production cutover. No existing app model, actual ledger, screening schedule, retained object, RLS policy or web display range changes. No new user data is committed. The established private Notion databases remain in place.

## Implemented and independently testable

1. Security identity contracts preserve six-character alphanumeric Korean codes, listing market, instrument type, quote currency and Notion page identity. ETF is an asset type, not an exchange. Existing Notion reporting amounts are not reinterpreted as listing-currency amounts.
2. One logical ACTUAL event journal supports buy, sell, dividend, interest, fee, tax, deposit, withdrawal, two-legged FX, account transfer and explicit corporate-action legs. Separate MODEL series cannot enter ACTUAL. Original source IDs/revisions/hash and stable private evidence references are retained. Corrections/voids append a successor with a reason; valuation resolves and replays the full chain. This avoids incorrect inverse average-cost reversals.
3. Exact eight-place decimal arithmetic produces account/currency cash, unsettled cash, holdings, cost basis and marks. Missing opening balances, taxes, net broker cash, settlement dates, prices and same-date verified FX remain explicit unknowns. Opening cash is settled cash immediately before that date; outstanding pre-opening trades must be present in the event inputs and are settled only once. Configured capital is never invented as a deposit. Market marks are dated and never drawn from the future. Valuations explicitly distinguish latest-revision RESTATED mode from AS_KNOWN mode with a recorded/available-time cutoff. Conflicting marks are quarantined. Performance is deliberately not computed from incomplete flows.
4. New adopted-Shadow series initialization freezes October 5 boundaries, 100m KRW starting funds per independent model, source/config/code versions and official initial FX. See `model-series-foundation.md` for detailed compatibility gates. Existing US A0/A2/B3 and KOSPI journals are not rewritten.
5. Later-inventory foundations: source/evidence links, optional strategy/signal/order linkage, reconciliation/correction log, immutable valuation and provenance archive contracts, Notion sync intent/ack/conflict planning. Allocator policy and CM research output are not fabricated.

## Offline migration planner

`npx vite-node --script scripts/plan-ledger-migration.ts PRIVATE_INPUT.json PRIVATE_OUTPUT.json`

The input contains captured legacy documents with their exact revisions, verified security identities, confirmed per-record broker/account mappings, an existing event list and capture timestamp. The output file is created exclusively with owner-only permissions. It has no write/apply mode and no Supabase client. Keep both files outside git; never commit personal transactions or raw receipts.

- Current sources: `portfolio_ledgers` for Korean/ETF executions and `us_actual_portfolio_ledgers` for US executions
- Do not re-import `portfolio_trades`, `portfolio_settings`, US model legacy actual fields or all Notion rows as current executions
- Same source/hash is a no-op; changed source requires a reviewed correction
- Similar economic events from separate sources are quarantined, never automatically merged; when both are new, neither wins based on input order
- Unknown account mappings stay unresolved; security names/markets are not evidence of account ownership
- Legacy fees are preserved but do not prove net settlement or tax inclusion

## SQL draft and permissions

`docs/ledger-foundation.sql` is additive review DDL, following this repository's SQL-document convention. It was not generated by a local Supabase migration tool, and must not be treated as executed or production-validated. It creates ten new tables. RLS limits authenticated SELECT to `auth.uid() = user_id`; writes are service-role INSERT only. No UPDATE/DELETE grants; triggers reject mutation. No SECURITY DEFINER function or unrestricted view. Existing grants/policies are untouched. No cascading deletion or retention deletion is introduced.

Before production application: verify on local/test PostgreSQL; generate a migration through the Supabase CLI; run advisors; exercise cross-user access, concurrent revision insertion and immutable history; obtain explicit approval for the exact DDL, approved source manifests and rollout. Re-running this DDL intentionally fails rather than quietly accepting schema drift.

## Rollback

Disable a new integration or revert its application caller if necessary. Keep all appended journal rows and private objects. Do not drop populated tables, delete source objects, overwrite a completed model day, or clear event history as a rollback.

The model-session append RPC serializes every date of a series under one transaction lock. The generic object-store journal requires an exclusive cross-process writer lease and must not run against an uncoordinated Storage adapter. Journal reads use a single-statement JSON snapshot, avoiding concurrent offset-pagination drift.
