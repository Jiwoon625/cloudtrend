# Data API 명시적 권한 점검 — 2026-10-21

## 결론과 적용 범위

10월 20일 Supabase 메일 원문(Gmail message `1a15861bbaa3d657`)과 연결된 공식 문서의 GRANT/RLS 구분을 확인했다. 기존 테이블 ACL은 유지되며, 10월 30일 이후 생성·재생성되는 테이블은 명시적 권한이 필요하다.

40개 마이그레이션, 33개 CREATE TABLE(공개 스키마 32개 + 비공개 bridge 1개)를 전수 재생·검증했다. 9개 테이블의 자동 권한 의존을 생성 파일에서 보완했다. RLS/정책, 실제 원장·승인대기함 쓰기 권한, 기본 권한 설정을 변경하지 않았다. anon GRANT는 추가하지 않았다.

- `screening_history`: 서비스 스크리닝 저장/갱신 및 기존 trim 흐름을 위한 서비스 CRUD.
- `portfolio_settings`, `portfolio_trades`, `portfolio_signal_log`: 기존 사용자 JWT 경로의 SELECT/INSERT/UPDATE만. DELETE·서비스 쓰기를 새로 부여하지 않는다.
- 미국 ingest/history/registry/snapshots/trades 5개: 서비스 자동화·재실행 경로 CRUD. authenticated의 모델 쓰기를 열지 않는다. 이후 마이그레이션의 실제 체결 열 UPDATE 제한은 그대로 적용된다.

## 검증과 운영 반영

`node tests/data-api-grants.test.mjs`는 외부 접속 없는 PGlite PostgreSQL에서 전체 40개 SQL을 파일 순서대로 실행한다. Auth/Storage의 최소 플랫폼 객체는 테스트 fixture이며 실제 Supabase 플랫폼을 재구현한 것은 아니다. 테이블 자동 GRANT를 전혀 만들지 않아 새 기본 정책을 재현한다.

검증 항목: 모든 public 테이블의 역할별 정확한 테이블 ACL과 RLS, 열 UPDATE 범위, anon RPC 차단, 소유자 INSERT/UPDATE/SELECT, 타 사용자 읽기·쓰기 차단, 서비스 저장·수정·삭제, append-only 쓰기 제한, 승인대기함 소유자 전이, 추가 GRANT의 재적용 멱등성. GitHub Actions에서 마이그레이션 변경마다 동일 검사를 수행한다. 기존 이력 보존 검사의 `tests/migration-history-manifest.json`도 변경한 생성 파일 4개에 한해 새 SHA-256으로 갱신했다. 해시 검증 자체와 나머지 역사 파일 고정은 유지한다.

운영 Supabase에는 **읽기 전용 카탈로그 점검만** 수행했다. 누락 대상으로 분류한 9개는 운영에서 이미 필요한 권한을 보유한다. 따라서 새 전진 마이그레이션이나 운영 GRANT 실행이 필요하지 않다. 수정한 생성 파일은 새 프로젝트/브랜치/reset에서 사용된다. 운영 migration history를 삭제하거나 과거 SQL 전체를 재실행하지 않는다. 현재의 데이터 변환·백필 마이그레이션들은 임의 재실행을 보장하지 않으며, 정상 migration runner의 한 번 적용을 전제로 한다.

실제 운영 PostgREST GET(`select=*&limit=0`)에서 anon은 승인대기함·원장 event_versions·미국 이력을 401/42501로 차단당했다. 포트폴리오 설정은 기존 자동 ACL이 남아 200 빈 결과였다(비로그인 auth.uid()=NULL, RLS로 행 차단). 이 기존 ACL은 이번 작업에서 변경하지 않았다. 테스트를 위해 실제 거래나 승인 데이터를 생성·갱신하지 않았다. 로그인 소유자 JWT 및 서비스 키를 사용한 운영 HTTP 쓰기 테스트는 수행하지 않았으며, 역할별 쓰기는 격리 PostgreSQL에서 검증했다.

## 발견된 운영 차이와 한계

- 운영 `collector_run_locks`는 저장소 40개 마이그레이션에 생성 정의가 없다. 현재 RLS 활성화, anon/A 권한 없음, S SELECT/INSERT/DELETE가 명시되어 있어 기존 운영에는 이번 변경의 영향이 없다. 하지만 새 프로젝트의 수집기 전체 재현에는 별도 수집기 스키마의 원본/설치 경로 확인이 필요하다. 이번에 추측한 DDL을 추가하지 않았다.
- `_cloudtrend_drive_ingest_chunks`는 운영 public 테이블 목록에 없으며 애플리케이션 참조도 없다. SQL-owner 전용 임시 객체로 유지한다.
- 보안 Advisor의 기존 경고는 소유자 전용 SECURITY DEFINER RPC 5종 및 유출 비밀번호 보호 비활성화다. private/서비스 전용 테이블의 RLS 정책 부재 INFO는 의도적 직접 접근 차단이다. 이번 변경으로 인증·RPC 정책을 수정하지 않았다.
- 전체 Supabase 로컬 스택의 `db reset` 및 로그인 사용자의 운영 UI 왕복 검증을 수행한 것으로 표현하지 않는다. 전체 SQL 재생은 임시 PostgreSQL에서 검증했다.
